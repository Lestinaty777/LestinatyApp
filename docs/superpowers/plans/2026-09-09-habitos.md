# Hábitos Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the persistent Habits category with the Today-first UI, five real analytical categories, habit detail, and Supabase-backed progress.

**Architecture:** PostgreSQL owns habits, versioned plans, daily records, optional contexts, and explicit connections under `habitos_` tables. A security-invoker RPC derives the dashboard from source records and the Expo module maps its DTO into a Today-first screen plus category and habit-detail routes. The Habits upper area reuses the current Home visual primitives rather than creating a second visual language.

**Tech Stack:** Expo Router 57, React Native 0.86, TypeScript, Vitest, TanStack Query, Supabase/PostgreSQL, lucide-react-native.

**Spec:** `docs/superpowers/specs/2026-09-09-habitos-design.md`

## Global Constraints

- Use the SQL-safe `habitos_` prefix for every table owned by this module.
- Never expose `privacidad`; all user-owned `public` rows enforce ownership with `auth.uid()` RLS.
- No client mutation accepts `usuario_id`; Supabase derives it from the authenticated JWT.
- The entry category is **Hoy** and renders the `habitos.png` composition without upper illustrations.
- Copy the current Inicio upper layout: left widgets, right illustration space, and horizontal category cards; add only a left Lucide `ChevronLeft` beside the current greeting.
- The five analytical categories are Hoy, Patrones, Conexiones, Riesgo and Impacto. Use real records or an explicit empty/observing state, never invented metrics.
- Use `TabChanger` for the Categorías/Hábitos switch and retain backward compatibility for its existing callers.
- Use `lucide-react-native` for every new icon.
- Do not implement the supplied upper illustrations; reserve their layout space only.

- [ ] **Step 3: Create the migration with tables and immutable history constraints**

Implement all six `public.habitos_*` tables described in the spec. Use `uuid` primary keys, FK cascades from items to plans/records, `unique(habito_id, fecha_local)` on records, non-negative record values, and `exclude using gist (habito_id with =, daterange(desde_fecha, coalesce(hasta_fecha, 'infinity'::date), '[)') with &&)` on plans after enabling `btree_gist`.

```sql
create table public.habitos_items (
  id uuid primary key default gen_random_uuid(),
  usuario_id uuid not null references public.perfiles_usuario(id) on delete cascade,
  titulo text not null check (char_length(trim(titulo)) between 1 and 80),
  descripcion text check (descripcion is null or char_length(trim(descripcion)) <= 280),
  icono_lucide text not null,
  color text not null,
  tipo_meta text not null check (tipo_meta in ('check', 'cantidad', 'duracion')),
  unidad text,
  estado text not null default 'activo' check (estado in ('activo', 'pausado', 'archivado')),
  created_at timestamptz not null default now(), updated_at timestamptz not null default now(), archivado_at timestamptz,
  check ((tipo_meta = 'check' and unidad is null) or (tipo_meta in ('cantidad', 'duracion') and char_length(trim(unidad)) between 1 and 32))
);
```
